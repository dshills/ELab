# Automatic storage failure and retry

If automatic recovery cannot write or scan its configured folder, `snapshot.recovery.error` reports the failed attempt. The native status says **Autosave needs attention**, and Autosave & recovery retains the detailed error. Your open document stays dirty and editable; the explicit manually saved project is not replaced by a recovery attempt. The normal timer retries automatically after storage becomes available again. Manual Scan/Checkpoint is not required for this retry.

An intervening drawing/value edit no longer hides the failed attempt or a successful retry. Automatic publication is guarded by the configured store and recovery-catalog generation, rather than by every application command. Newer recovery/configuration/save publications and shutdown still prevent an older filesystem result from replacing their state. Explicitly cleared recovery selection remains cleared. Stored snapshots retain their captured document; a successful older capture does not mark subsequent edits saved or replace the current graph/history/physics.

A successful manual Save establishes this fence before its recovery cleanup unlocks the editor. If an edit arrives during cleanup and the cleanup's own status is withheld, older automatic results still cannot re-list a capsule that Save retired. A blocked-cleanup regression reproduces that gap in the intermediate guard and verifies the combined repair.

The guard repair was driven by a reproduced failure: an actual unavailable owned directory produced a filesystem error, then an ordinary resistor edit before publication caused the error to disappear. Controlled tests now require that error, preserve the later editor state, repair storage, publish a successful captured retry across another edit and inspect the exact older captured value. Additional cases protect a newer scan, manual save, configuration, closed service and empty selection from stale results/errors.

The [public workflow](../scripts/recovery-failure-demo.py) uses a recorded RC circuit and the ordinary two-second schedule. It first obtains an automatic complete capsule, temporarily moves only its owned recovery folder and places an owned regular file at that path. It continues resistance edits until an automatic error is visible, confirms the previous capsule/manual source bytes are intact, commits a final 50 kΩ edit, restores the folder and waits for an automatic complete retry. The entire expected document and original 200 ms kept recording must match; no manual recovery scan/checkpoint substitutes for automatic behavior.

Both native and agent workflows invoke the same commands. A native descriptor test additionally observes the actual background failure/status/detail and their clearing after retry. This establishes those semantic controls, not complete physical input, screen-reader or pixel/readability acceptance. Real fault injection here covers a cooperating unavailable directory on the recorded workstation; it does not cover every filesystem/device failure, power loss or hostile writers. The separate [timing series](recovery-timing.md) records the earlier named-fixture measurements; this repair retains its schedule and writer but is not a new 240-sample benchmark.

[Validation receipt and complete evidence](validation/recovery-failure-validation.json) retain the original failure, final checks, public state/capsule/source artifacts and qualified private candidate identity. Application commands, project/recovery formats, models, numerical methods, capacity/work limits and canonical app bundles remain unchanged.
