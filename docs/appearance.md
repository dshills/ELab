# Appearance and compact native controls

Choose **Light**, **Dark**, **System**, or **Apollo** in the header theme menu. `appearance.theme.set {"theme":"apollo"}` changes the same preference through the agent API; `project.inspect.theme` reports it. The discovered input schema lists all four permitted values. Ordinary revision and retry guards apply.

Apollo follows the owner's instrument-console reference: near-black blue panels, cyan outlines and lettering, bright cyan selected controls, and compact Roboto Mono labels. The typeface is already included in the UI runtime. Amber remains available for scope signals, with coral warning text. Thin outlines and square control corners retain the existing layout, native focus indicators and interaction behavior. Schematic symbols, grid, scope traces, component browser, inspector and scrollbars use the same session palette. This is an interpretation for a readable electronics workspace, not a replica of spacecraft controls. Apollo remains selected regardless of the system's Light/Dark appearance and uses the same persistence as the other themes.

Appearance defaults to Light until a configured preference file is loaded. It survives project replacement and is restored across launches by the independent preference store described below. System resolves the native backend's current appearance. Colors are resolved for each descriptor tree without changing macOS settings or mutating Vellum's startup theme. Panels, fields, labels, selected controls, schematic symbols/grid/pinned cards, and scope axes/traces use the selected palette. On macOS, File, Examples and Theme use real AppKit menus installed by Vellum’s native menu service. The same menus also appear in the macOS menu bar after opening a header menu. Other platforms retain Vellum MenuButton. An app-scoped native adapter styles scrollbar tracks/handles and diagnostic disclosure headings without changing the SDK checkout or system appearance.

Theme commands do not restart simulation, change charge/time/run/electrical revision, alter document dirty state, or add history. Invalid values are refused before mutation. Core and native regressions cover these invariants and menu/agent parity.

File actions and examples preserve existing command enablement and unsaved-change/generation protection. macOS popup presentation is asynchronous and uses Vellum’s existing registry callbacks; obsolete/shutdown callbacks retain the service’s validation. Drawing and live/recorded scope controls use Toolbar with explicit content height and horizontal overflow with room for their controls and any overflow bar rather than disappearing when compressed. Rails apply consistent descendant widths and text wrapping; inputs use readable local foreground/background colors. The initial window is 1040 × 760 device-independent units; rails scroll independently.

See [the UI audit and screenshots](../research/ui-audit/README.md) for observed results and remaining limits. This does not establish full keyboard, IME, screen-reader, or clean-distribution qualification.

## Persistent preferences

Desktop startup now loads and autosaves a separate `elab.appearance` version 1 JSON file at `os.UserConfigDir()/ELab/appearance.json`. It stores only the theme, is bounded to 4096 bytes and is created with private file permissions. Circuit files and their format remain unchanged. Override the location with `--appearance-file PATH`, or use `--no-appearance` for a session-only theme. Native smoke uses an isolated temporary profile. Headless sessions opt in with `elab-agent --appearance-file PATH`.

`appearance.configure {"path":"/absolute/path/appearance.json"}` admits background loading and autosaving; `{"path":""}` disables the store without changing the visible theme. `project.inspect.appearance` reports loading/saving/ready/error/disabled, the current or last-used path, last saved theme, and failure text. `appearance.wait {}` waits up to five seconds for loading/saving to settle; inspect status/error even after a successful wait. The Inspector offers the same enable/session-only controls and explicit saved-theme reload after a failure.

An accepted later theme choice, including selecting the already visible value, supersedes an older pending load. Changes are coalesced to the latest theme. Reading, preparing, syncing and publishing files run outside the editor lock; at most two store workers can exist while older work unwinds. Writes use the existing atomic file publisher and captured file identity/hash, refusing links, invalid/oversized data and external changes. Errors keep the selected in-memory theme and original file; explicit reconfiguration reloads/resynchronizes the saved preference. Publication already underway can finish after disabling/reconfiguration; it never updates a replacement store's state. OS calls can outlast cancellation/deadlines.

Service shutdown admits Close immediately, wakes the store, and waits outside the editor lock for its final captured choice to flush. Filesystem failures remain inspectable and are not silently overwritten. Preference publications use the observer `preferences` and `jobs` topics. Discovery reuses local `urn:elab:object-id:1` for common ID parameters, preserving schema registry version 2 and existing transport budgets.

### Identified appearance work

Nonempty configuration and each theme choice while persistence is configured and healthy return a distinct `snapshot.appearance_work`. Retain its `id` and query `appearance.work.inspect {"id":"appearance-1"}` for its captured actor, input/command revisions, document/run identity, path, requested theme, progress and outcome. The snapshot holds only the latest job. A completed job reports its result theme and SHA-256 of the file it read or published; `published` distinguishes a write from an already matching file. These are historical outcomes, not assertions about later external changes. `current_at_completion` describes only the instant the job completed.

`appearance.work.cancel {"id":"appearance-1"}` uses the same mutation guards and retry key as other commands. It disables the current store before publication, preserving the visible theme and prior file. A blocked read or preparation remains `canceling` until it returns. A superseded ID cannot cancel its replacement. Once atomic publication has begun, cancellation refuses `operation-committing`; reconfiguration/disable can still detach that store, and its retained job records the actual later artifact or failure. No published file is rolled back.

Statuses are `queued`, `running`, `canceling`, `completed`, `failed`, `canceled` and `superseded`. Coalesced choices can end as superseded without writing. An older publisher can complete with `superseded:true` and `current_at_completion:false`. Up to 32 jobs are retained; admission evicts the oldest terminal record, preserving active work. Unknown/evicted IDs refuse `operation-unavailable`. Job metadata survives project replacement. Disabled or failed stores accept session-only theme choices without admitting a job; compare the latest job's `command_revision` with the command response to determine whether new work was admitted.

`appearance.wait` retains its global compatibility behavior. It does not wait for older detached/canceling jobs; inspect each retained ID for that outcome. Events coalesce and may skip intermediate phases. The two public commands (164 total) and optional snapshot field are now packaged in [clean /171](../research/ui-audit/first-version/appearance-work-review-checkpoint.json); preserved /170 retains the global-only implementation. [Source validation](validation/appearance-work/README.md) and [copied signed runtime/archive validation](validation/appearance-review-171/README.md) retain their separate scopes and limits.

Native styling callbacks now read a complete immutable palette through an atomic pointer, and dark-theme traces/pinned readings use brighter theme colors. Idle OS theme changes, custom palettes, native menu checkmarks and complete interaction/accessibility qualification remain separate work.

The native verification harness accepts `--smoke --smoke-timeout 90s` for race-instrumented builds (maximum two minutes); the default remains 20 seconds. This changes only the harness deadline, never simulator work/time limits.
