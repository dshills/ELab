# Autosave can be turned off during a storage fault

Both configuration aliases previously scanned the recovery folder before disabling its timer. The initial regression replaces only an owned directory with an owned regular file and shows that waiting disable returns `file-error`, while the start form fails its job. The control was unusable precisely while storage needed attention.

Same-store disable now applies only scheduling/interval state without opening/scanning that configured folder. It retains the store/lease and last-known error/catalog/selection, reports configuration applied but catalog not refreshed, and fences late checkpoint publication. New-store and enable preparation remain ordinary validated/scanned operations. Native status says autosave is off with the last recovery error; the toggle still invokes the same public start command.

Core race tests cover both aliases on unavailable storage, immutable source/capsule bytes and editor state, an already captured write finishing after disable without replacing status, cancellation, bad interval/different-store refusal and on-demand semantics. Native callback testing observes a real automatic error, disables through the user toggle, retains the detailed error/off wording and re-enables into a complete new snapshot after storage repair. The completion note describes existing recovery state without implying a newer catalog observation. Production native inventory review covers `desktop/view.go` and `desktop/project_work.go`; 57 files, 388 sites, 162 commands and 132 routed IDs remain, with command/alias/site semantics unchanged.

The public rehearsal extends the existing recorded-RC interruption workflow. It disables through both aliases, refuses enable while unavailable, repairs storage while remaining off for at least three seconds without file/catalog changes, then explicitly enables and captures the latest 50 kΩ graph with the original recording. The first checker used a shortened field name; the corrected protocol uses the existing `recovery_catalog_applied` JSON field rather than changing product output. See [behavior/protocol](../docs/recovery-disable.md) and [validation receipt](../docs/validation/recovery-disable-validation.json).

This is a bounded control/recovery improvement. An already captured write may finish; disabling is not a filesystem cancellation or deletion command. No new model, numerical method, application command, file format or work limit is introduced. General device failures, physical input/accessibility, distribution, printing and participant gates remain separate; the continuing MVP goal stays active.

Final public headless/native disable calls complete in **2.075 /0.928 ms** for these individual local workflow runs. Both aliases succeed, report no catalog refresh and retain the last error/catalog. An attempted enable while the directory is unavailable refuses without changing disabled state. After repair, available storage remains off for **3.011258 /3.008653 s** with identical file sets/hashes and recovery observations. Explicit enable then produces the exact latest 50 kΩ document in **0.500627 /0.468557 s**, retaining the original **209 captured rows** and unchanged manual source/last complete capsule. These are named workflow measurements, not a latency distribution or universal bound.

Legacy configuration, owner protection and real SIGKILL workflows also pass. The owned native host closes normally.
